## 4. Гипотезы о причинах нулевого результата

| # | Гипотеза | Как проверить |
|---|---|---|
| H1 | Часть файлов — **сканы**, текстового слоя нет, OCR не отработал (путь к Tesseract задан жёстко, возможна тихая ошибка) | Открыть PDF, попытаться выделить текст; посмотреть логи OCR |
| H2 | **Сломано разбиение на разделы**: заголовки ищутся по `\n`, а текст слит в одну строку, поэтому разделов с конструкциями не находится | Вывести число найденных разделов для 2–3 «пустых» отчётов |
| H3 | Конструкции ищутся по узкому списку слов; в реальных отчётах используются другие формулировки | Сравнить текст отчёта со словарями `01_constructs` |
| H4 | Фильтры `'см'`/`'рис'` по подстроке вырезают нужные фрагменты | Проверить, сколько текста остаётся после фильтрации |
| H5 | Ошибка при обработке подавляется (try/except), результат записывается как «0» | Просмотреть код и логи на перехват исключений |
| H6 | Отчёт № 13 отличается по структуре (текстовый PDF, стандартные заголовки), потому и обработан | Сравнить формат № 13 с «пустыми» |

# Система анализа PDF-отчётов о техническом состоянии зданий

## Краткое описание

Проект представляет собой систему анализа PDF-отчётов о техническом состоянии зданий. Система извлекает текст из PDF, при необходимости использует OCR, классифицирует состояние строительных конструкций, формирует описание дефектов, рассчитывает приоритет здания, сохраняет результаты в SQLite и отображает их через Streamlit-интерфейс. Дополнительно реализованы RAG-поиск по базе конструкций, сравнение отчётов и экспорт данных.

## 1. Локальная модель

В проекте развёрнута локальная LLM:

**Qwen/Qwen2.5-1.5B-Instruct**

Она используется в двух обёртках:

- `unified_analyzer_re.py` — класс `LLMEngine`;
- `llm_analyzer.py` — класс `LocalLLMAnalyzer`.

Фактически это instruction-tuned causal language model на 1.5B параметров. В комментарии `llm_analyzer.py` упоминается TinyLlama, но по коду модель по умолчанию — **Qwen2.5-1.5B-Instruct**.

Особенности загрузки и инференса:

- загрузка через `transformers`: `AutoTokenizer`, `AutoModelForCausalLM`;
- при наличии CUDA используется `torch.float16`, `device_map="auto"`;
- на CPU используется `torch.float32`;
- `pad_token` при необходимости устанавливается равным `eos_token`;
- генерация: `temperature=0.3`, `top_p=0.9`, `repetition_penalty=1.1`, `max_new_tokens=150` в `LLMEngine` и `250` в `LocalLLMAnalyzer`;
- после генерации выполняется очистка ответа от служебных маркеров, эмодзи и мусорных фраз;
- LLM не дообучается в этом проекте — используется только inference.

LLM применяется для генерации кратких описаний состояния конструкций. Если LLM не загружена или ответ некачественный, используется шаблонный fallback.

## 2. Состав проекта

| Файл | Назначение |
|------|------------|

| `main.py` | Извлечение текста из PDF, OCR, разбиение на секции, ML-классификация конструкций, расчёт приоритета |

## 3. Основной пайплайн анализа

1. **Загрузка PDF** через Streamlit.
2. **Извлечение текста**:
   - `pypdf`;
   - если текста меньше 500 символов — OCR через `pytesseract` + `PyMuPDF/fitz`;
   - путь к Tesseract в `main.py` и `app.py` жёстко задан под Windows.
3. **Определение здания**:
   - по адресу/городу/первым строкам через регулярные выражения;
   - формируется `building_id`.
4. **Проверка дубликата**:
   - MD5-хеш PDF;
   - если отчёт уже есть в БД для этого здания — повторно не анализируется.
5. **ML-анализ**:
   - разбиение текста на секции: фундамент, стены, перекрытия, крыша, лестницы, выводы;
   - поиск конструкций по ключевым словам;
   - выбор лучшей цитаты с приоритетом на дефекты;
   - классификация статуса: `НОРМАТИВНОЕ`, `РАБОТОСПОСОБНОЕ`, `ОГРАНИЧЕННО-РАБОТОСПОСОБНОЕ`, `АВАРИЙНОЕ`;
   - fallback на правила, если ML-модели не загружены.
6. **RAG-контекст**:
   - поиск похожих конструкций в FAISS-индексе;
   - контекст передаётся в генератор описаний.
7. **Генерация описания**:
   - локальная LLM Qwen2.5-1.5B-Instruct;
   - при неудаче — шаблон.
8. **Расчёт приоритета здания**:
   - `КРИТИЧЕСКОЕ`, если есть угроза обрушения или судебное решение о расселении;
   - иначе взвешенная оценка по секциям;
   - рассчитывается `health_index`.
9. **Сохранение**:
   - PDF в `data/reports/<building_id>/<hash>.pdf`;
   - отчёт и конструкции в SQLite `data/reports.db`.
10. **Отображение**:
    - общий вердикт;
    - статистика по статусам;
    - группировка по осям/подъездам/секциям;
    - категории конструкций;
    - аварийные конструкции;
    - рекомендации;
    - сравнение отчётов.

## 4. ML-модели и методы обучения

Обучение реализовано в `train_ml_model.py`. Обучение LLM не выполняется — обучаются только классификаторы состояния конструкций.

### Входные данные

Ожидается CSV-файл:

Поддерживаются разные кодировки и разделители. Ожидаются колонки с текстом и классом. Классы:

- `0` — нормативное;
- `1` — работоспособное;
- `2` — ограниченно-работоспособное;
- `3` — аварийное.

### Аугментация данных

В `train_ml_model.py` есть аугментация:

- замена ключевых слов синонимами: коррозия, трещина, скол, износ, обрушение, усиление, ремонт и др.;
- добавление типовых фраз для аварийного и работоспособного классов;
- коэффициент аугментации по умолчанию `augment_factor=2`.

### Компоненты ансамбля

1. **SBERT-эмбеддинги**
   - модель: `paraphrase-multilingual-MiniLM-L12-v2`;
   - классификатор: `LogisticRegression` с `class_weight='balanced'`, `C=2.0`, `solver='saga'`;
   - калибровка: `CalibratedClassifierCV`, `method='isotonic'`, `cv=3`.

2. **TF-IDF + LinearSVC**
   - `TfidfVectorizer`: `max_features=12000`, `ngram_range=(1,3)`, `min_df=2`, `sublinear_tf=True`, `max_df=0.85`;
   - `LinearSVC`: `C=1.5`, `class_weight='balanced'`, `max_iter=5000`, `dual=False`;
   - калибровка вероятностей: `CalibratedClassifierCV`, `isotonic`, `cv=3`.

3. **Ручные признаки**
   - длина текста;
   - число слов;
   - количество слов-маркеров опасности/ограничений/безопасности/технических описаний;
   - наличие чисел, мм, процентов;
   - максимальные значения мм и процентов;
   - соотношения между группами маркеров;
   - всего 14 признаков;
   - масштабирование `StandardScaler`.

4. **Мета-классификатор XGBoost**
   - вход: вероятности SBERT + вероятности TF-IDF/LinearSVC + масштабированные ручные признаки;
   - обучается 3 XGBoost-модели с разными параметрами;
   - итоговое предсказание — усреднение вероятностей;
   - параметры моделей различаются по `n_estimators`, `max_depth`, `learning_rate`, `subsample`, `colsample_bytree`.

### Правила постобработки

После ML применяются правила:

- жёсткие ключевые слова для аварийного состояния: `аварийн`, `обруш`, `сквозн`, `прогнил`, `угроза`, `предельное состояние` и др.;
- ключевые слова работоспособного состояния: `работоспособное`, `несущая способность обеспечена`, `осадки стабилизировались`, `запас прочности`;
- отрицания: `не выявл`, `отсутств`, `не обнаруж`;
- числовые пороги: трещины/прогибы более 2 мм, проценты более 25%, коэффициент использования более 0.9 и т.п.;
- если модель уверена более чем на 85%, ей доверяют.

## 5. RAG-подсистема

Реализована в `rag_analyzer.py`.

- Эмбеддер: `SentenceTransformer('paraphrase-multilingual-MiniLM-L12-v2')`.
- Индекс: FAISS `IndexFlatL2`.
- Индекс сохраняется в `rag_index/`:
  - `faiss_index.bin`;
  - `records.pkl`;
  - `documents.pkl`.
- Из PDF извлекаются:
  - адрес;
  - год;
  - конструкция;
  - категория;
  - статус;
  - дефект;
  - цитата;
  - исходный файл.
- Поддерживается поиск:
  - по запросу;
  - по статусу;
  - по категории;
  - по адресу.
- Есть CLI-режим для индексации и поиска.

RAG используется в `unified_analyzer_re.py` для передачи похожих примеров в генератор описаний.

| **Немедленно** | Ввести отдельный статус **«НЕ УДАЛОСЬ ПРОАНАЛИЗИРОВАТЬ / ТРЕБУЕТ РУЧНОЙ ПРОВЕРКИ»** для отчётов с 0 конструкций. Не показывать им «НИЗКИЙ» и зелёный цвет |
| **Немедленно** | Показывать диагностику при пустом результате: тип файла, число страниц, длина текста, причина |
| **Скоро** | Найти и исправить причину нулевого результата (разбиение на разделы, OCR, словари) |
| **Скоро** | Логировать исключения вместо их тихого подавления |

## 8. Streamlit-приложение

`app.py` предоставляет:

- загрузку нескольких PDF;
- кнопку анализа;
- прогресс обработки;
- проверку дубликатов по хешу;
- вывод всех обработанных отчётов;
- детальный просмотр отчёта:
  - общий вердикт;
  - приоритет;
  - `health_index`;
  - статистика по статусам;
  - группировка по осям/подъездам/секциям;
  - категории конструкций;
  - аварийные, ограниченные, работоспособные и нормативные конструкции;
  - цитаты и LLM-описания;
  - рекомендации;
- сравнение двух отчётов;
- сравнение со всеми отчётами по зданию;
- повторный анализ;
- проверку судебных решений о расселении по ключевым фразам.

При наличии судебного решения приоритет принудительно повышается до `КРИТИЧЕСКОЕ`.

## 9. Расчёт приоритета

В `main.py` реализован `calculate_priority()`.

- Если есть угроза обрушения или судебное решение — `КРИТИЧЕСКОЕ`, `health_index = 0`.
- Иначе используется взвешенная оценка по секциям:

| Секция | Вес |
|--------|-----|
| фундамент | 30 |
| стены | 35 |
| перекрытия | 20 |
| крыша | 10 |
| лестницы | 5 |
| выводы | 0 |

Статусы имеют баллы:

| Статус | Балл |
|--------|------|
| НОРМАТИВНОЕ | 0 |
| РАБОТОСПОСОБНОЕ | 1 |
| ОГРАНИЧЕННО-РАБОТОСПОСОБНОЕ | 3 |
| АВАРИЙНОЕ | 10 |
| НЕ ОПРЕДЕЛЕНО | 2 |

Далее рассчитывается `raw_score`, а `health_index = 100 - raw_score`. Пороговые уровни приоритета: высокий, средний, низкий.

## 11. Технические замечания

- Tesseract OCR настроен на жёсткий Windows-путь: `C:\Program Files\Tesseract-OCR\tesseract.exe`.
- Комментарий в `llm_analyzer.py` о TinyLlama устарел: фактически используется Qwen2.5-1.5B-Instruct.
- LLM не дообучается; качество описаний зависит от промпта и очистки ответа.
- ML-модели загружаются из `.pkl`; если файлов нет, используется rule-based fallback.
- SQLite и файловое хранилище локальные, без авторизации и многопользовательской блокировки.
- В `app.py` есть потенциально проблемные места с областью видимости `row` в блоке детального отчёта — при доработке стоит проверить.
- Для полноценной работы нужны зависимости: `streamlit`, `pandas`, `pypdf`, `pytesseract`, `Pillow`, `PyMuPDF`, `torch`, `transformers`, `sentence-transformers`, `faiss`, `scikit-learn`, `xgboost`, `joblib`, `numpy`.
